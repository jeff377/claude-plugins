# 交接工作給接手的 session

擬定的那個 session 累積了大量討論脈絡，接手的人用不到；而動工那一端要讀大量原始碼、
既有產出或參考資料，還要跑測試與查證，適合乾淨的 context。
因此「設計定案 → 換 session 動工」是常見且正確的切換點。

**接手的不一定是寫程式。** 撰寫系列文章、批次遷移、資料清理、文件改版都適用。

**也不一定有一份叫 plan 的檔案。** 本 skill 統稱新 session 必須先讀的東西為**交接文件**，
它可以是：

- `docs/plans/` 下的一份 plan（最常見）
- 放在別處的規格或設計文件
- **一組文件**——例如連載系列的大綱 + 逐篇筆記 + 寫作規則，三份都要讀
- 甚至沒有文件，只有一段口頭定案的需求（此時 prompt 本身就是交接文件，
  必備內容一項都不能少，而且要寫得更完整）

判別法只有一個：**下一步要不要換一個乾淨的 context 去做。**

本 skill 規範**交接時要做哪些動作**、**要輸出什麼**，以及**用哪種方式把它交出去**。
其中「先把交接文件 commit」與「prompt 必須明寫工作樹期望」是硬性步驟，
不是可以憑記憶重現的格式範本。

---

## 交接方式：優先用 spawn task，否則輸出可複製的 prompt

不論走哪條路，**prompt 的內容要求完全相同**（見下方「必備內容」與「範本」）。
差別只在遞送方式。

### 首選：`spawn_task`（CCD app 環境）

環境有 `spawn_task` 這類工具時用它——把交接 prompt 當作 task 的 prompt 送出，
使用者點一下就會在**新的 session** 裡開始。

- **仍由使用者點擊才啟動**，控制權沒有交出去——只是把「複製貼上」換成「點一下」。
- **啟動時可選 worktree 或 local only，預設是建 worktree**（實測 2026-08-01：未選
  local only 送出的 task，跑在 `.claude/worktrees/` 底下、掛在自動產生的
  `claude/*` 分支上）。

> ⚠️ **有 `spawn_task` 卻改用「把 prompt 寫成檔案傳給使用者」是明確的錯**
> （實測 2026-08-11 踩過）。傳檔案看起來也是「交出去」，但少掉的正是這個 skill 的價值：
> 使用者得自己開 session、自己貼、自己記得選 local only。
> **判別法：這個環境有沒有 `spawn_task`？有就用它，沒有才退回可複製 prompt。**

> **交接 prompt 必須明寫工作樹與分支的期望**，例如「請在主工作樹的 main 上進行」
> 或「這個任務適合開 worktree」。沒寫的話，使用者可能按預設開了 worktree，而 prompt 裡
> 「依 repo 慣例直接提交 main」之類的指示就會與實際環境對不上，得中途導正。
>
> 走 worktree 時還要注意：**主工作樹尚未 commit 的內容在 worktree 裡看不到**
> （新檔案不存在、已修改的是舊版），新 session 會照著一份它讀不到的文件動工且不報錯。
> 這正是下方「交接前檢查」堅持先 commit 的理由。
>
> ⚠️ **交接文件若位於 gitignored 目錄或另一個 repo，一律只能走 local only**，
> 且 prompt 開頭就要寫明原因（worktree 裡那個目錄根本不存在）。
> 實例：主 repo 把 `docs/blogs/` 設為 gitignored，而它自己是一個獨立的 git repo。

> 別把它當成背景執行的 agent：它是一個獨立 session，有自己的對話與 context，
> **不會主動把結果回報進本 session**（沒有 push）。
> 但**可以主動去讀**（pull）—— 見下方「交接後：可以自行監控結果」。

### 備援：輸出可複製的 prompt

沒有這類工具時（純 CLI、其他介面），把 prompt 放進**單一 fenced code block**
（純文字，不加 `bash` 之類語言標記——那會讓部分介面顯示成可執行指令），
由使用者自行開新 session 貼上。

**`spawn_task` 不可攜**，所以 skill 不能只寫這一條；備援路徑必須保留。

### 走 local only / 手動開 session 時：共用工作樹

選 local only 的 spawn task、或使用者手動開一個不加 `--worktree` 的 session，都會與本
session **共用同一棵工作樹**。兩邊同時改同一批檔案會互相覆蓋，所以下方「交接後」的
**交接即交棒**不是建議而是硬要求。（走 worktree 則無此問題，但換成上面那個
「讀不到未 commit 的內容」的風險。）

## 交接前檢查（兩項，缺一不可）

### 1. 把交接文件簽入（commit）

**交接的第一個動作就是把交接文件 commit 掉**，不是「詢問要不要 commit」。
這是交接流程的一個步驟，不是一個選項——交接本身就是使用者對這個動作的授權。

理由：新 session 可能開在 worktree（**讀不到主工作樹的未 commit 內容**，會照著一份
它打不開的文件動工且不報錯），也可能共用主工作樹（讀得到，但設計會與動工的改動
混在同一批 diff，之後難以分辨哪些是設計、哪些是產出）。兩種情境下先 commit 都較好。

流程：

1. `git status` 確認交接文件的狀態。**交接文件是一組時，每一份都要確認**
2. 未 commit（新增或已修改）→ **直接 commit**，訊息比照 repo 慣例
   （plan 類多為 `docs(plans): <主題>`，摘要寫階段數與是否為破壞性變更）
3. 已 commit → 取 commit hash
4. prompt 的 git 區塊寫上 **文件路徑 + commit hash + 目前分支**

**唯一的例外**：使用者明確表示這次不要 commit。此時 prompt 必須明寫
「交接文件尚未 commit，位於主工作樹」，且該任務**不可開 worktree**（只能選 local only）。

> 順帶檢查交接文件以外的相關檔案是否也該一併簽入——若新 session 需要參照的
> 樣板 / fixture / 設定檔 / 既有產出還躺在工作區，worktree 裡同樣看不到。

> ⚠️ **交接文件在另一個 repo 時，要 commit 的是那個 repo**，
> 並在 prompt 的 git 區塊**兩個 repo 的狀態都寫**。

### 2. 是否真的定案

若仍有「待定」「未決」段落，交接會讓新 session 在中途卡住或自行決定。
先確認這些項目已收斂，或在 prompt 中明確標示哪些仍待使用者拍板、遇到時應停下詢問。

⚠️ **已知的未決事項要逐條列進 prompt 並標「不要自行處理」**，光說「有些事還沒定」沒有用。

## 交接 prompt 的必備內容

| 區塊 | 為何必要 |
|------|---------|
| **交接文件完整路徑 + 「先完整讀過」** | 新 session 沒有任何討論脈絡。是一組文件就逐份列出，並說明各自放什麼 |
| **「設計已定案，不需重新討論」** | 否則新 session 會把已否決的方案重議一遍，浪費大量往返 |
| **出貨 / 順序約束** | 階段能否分開發布、是否有前置工作——最容易在中途才踩到 |
| **未驗證項目清單** | 區分「已證實的」與「仍需自行確認的」，避免新 session 誤信推測為事實 |
| **環境前置** | 容器 / 服務是否已啟動、需要哪些外部相依 |
| **git 狀態** | 交接文件與相關檔案是否已 commit、目前在哪個分支；**涉及多個 repo 就逐個寫** |

不需要塞進 prompt 的：交接文件內已寫的設計理由、被否決方案的完整論證、討論過程。
**那些是文件的職責**——若 prompt 需要複述才說得清，代表文件本身寫得不夠自足，
應該回頭補文件而不是加長 prompt。

### 額外一項：工作區若有別人的在途改動，要明寫

共用工作樹時，`git status` 可能混著其他 session 未完成的改動。
**把那些路徑逐一列進 prompt 並要求「不要碰、不要 commit」**，
同時指示用 `git commit -- <明確路徑>` 只提交自己的檔案，不要 `git add -A`。
沒寫的話，新 session 一個 `git add -A` 就會把別人的半成品提交進去。

## 範本

```
<一句話說明要做什麼——例如：實作 <文件路徑>／撰寫 <系列> 的第 N 篇>

先完整讀過：
- <文件 1 路徑> — <裡面放什麼>
- <文件 2 路徑> — <裡面放什麼>

設計已定案，不需重新討論其中的決策或替代方案（文件已記錄被否決的方案及理由）。

<工作樹與分支期望——例如：請選 local only 在主工作樹的 main 上進行，原因是 …>

<出貨 / 順序約束——例如：階段 1 與階段 2 必須一起發布，原因見 §X>

核心內容（詳見 §X）：
- <逐項列出，讓新 session 一眼看到規模>

<若為 breaking change：說明破壞面與 commit / CHANGELOG 的標記要求>

尚未定案、遇到時請停下詢問，不要自行處理：
1. <...>

尚未驗證、需要你自行確認的項目：
1. <...>

環境：<容器 / 服務狀態、前置條件>
git：<交接文件與相關檔案的 commit 狀態、目前分支；多個 repo 就逐個寫；
      工作區若有別人的在途改動，逐一列出並要求不要碰>
```

## 交接後

- **本 session 停止改動該工作涉及的檔案**，避免與接手的 session 衝突。
- plan 類文件的狀態列改為 `🚧 進行中`（格式見 `plan-write`）；多階段則更新對應階段列。
- 若交接後才發現交接文件有誤或遺漏，**改文件並告知使用者轉達**，
  不要在本 session 直接改動工涉及的檔案。

### 可以自行監控結果，不必等使用者轉述

交出去**不等於失去視野**。接手的 session 不會 push 結果過來，但本 session 可以 pull：
環境若有 session 管理工具（`list_sessions` / `list_events` 這類），就**自己去讀**，
不要停在「等使用者回報」。

1. `list_sessions` 依**標題與 `cwd`** 找出它的 sessionId（標題就是你送出時給的那個）。
2. `list_events` 讀它最近的 turn。想看更早的用回傳的 `before_uuid` 往前翻 ——
   **結論通常在中段**（動工前的觀察與判斷），最後幾筆多半只是 `(called Edit)`。

**順手驗一件只有這裡看得到的事**：它的 `cwd` 是主工作樹還是 `.claude/worktrees/…`？
這一眼就能確認 prompt 裡「請選 local only」或「適合開 worktree」的指示有沒有真的生效。
對不上就得馬上處理 —— 走錯的那一種正是上面兩個風險（讀不到未 commit 的內容 /
兩邊互相覆蓋）的來源。

**監控是唯讀的。** 發現它做錯或卡住時，動作仍是「改交接文件 + 告知使用者轉達」，
**不是自己動手改它正在動的檔案** —— 共用工作樹下同時改會互相覆蓋，這條不因為
「我在監控」而放寬。

沒有 session 管理工具時（純 CLI），才退回「等 spawn task 結束的通知」或請使用者轉述。

## 常見錯誤

- ❌ **有 `spawn_task` 卻把 prompt 寫成檔案傳出去** → ✅ 有就用 `spawn_task`，純 CLI 才退回可複製 prompt
- ❌ 因為「可能建 worktree」就整個不用 spawn task → ✅ 用它，並在 prompt 明寫要選哪一種
- ❌ 因為「這次沒有 plan 檔案」就不叫這個 skill → ✅ 交接文件不限是 plan，甚至可以只有 prompt 本身
- ❌ prompt 沒交代工作樹 / 分支期望 → ✅ 明寫「在主工作樹的 main 上進行」或「適合開 worktree」
- ❌ 交接文件在 gitignored 目錄或另一個 repo，卻沒禁用 worktree → ✅ 明寫只能 local only 並說明原因
- ❌ prompt 只寫「實作 docs/plans/plan-xxx.md」→ ✅ 補齊上表六個區塊
- ❌ 停下來問「要不要先 commit？」→ ✅ **直接 commit**，那是交接流程的步驟不是選項；
  只有使用者明確說不要時才走未 commit 路徑（並在 prompt 明寫狀態、禁用 worktree）
- ❌ prompt 的 git 區塊只寫分支、沒寫 commit hash → ✅ 兩者都寫
- ❌ 工作區有別人的在途改動卻沒寫進 prompt → ✅ 逐一列出並要求不要碰、不要 `git add -A`
- ❌ 把設計理由複述進 prompt → ✅ 那是文件的職責；prompt 只給指向與約束
- ❌ 交接後本 session 繼續改同一批檔案 → ✅ 交接即交棒（共用工作樹時同時改會互相覆蓋）
- ❌ 有 session 管理工具卻停在「等使用者回報結果」→ ✅ 自己 `list_sessions` + `list_events` 讀，
  順便從 `cwd` 驗證 local only / worktree 的指示有沒有生效
- ❌ 監控時順手改它正在動的檔案 → ✅ 監控是唯讀的；要導正就改交接文件 + 告知使用者轉達
- ❌ 用 ` ```bash ` 包裝交接 prompt → ✅ 用純文字 fenced block（避免被當成可執行指令）
