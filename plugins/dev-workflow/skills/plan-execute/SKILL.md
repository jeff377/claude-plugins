# 依 plan 實作時的驗證閘門

`plan-write` 管撰寫、`plan-handoff` 管交接，本 skill 管**執行期間**。

三條規則，各自對應一種實際發生過、且事後才被發現的失誤。規則刻意少——
每一條都要能指出「不做會怎樣」，做不到的就不該進來佔位。

---

## 1. 動筆前確認 plan 版本

**以 git 的內容為準，不要用 session 早期讀過的版本。**

```bash
git log --oneline -1 -- <plan 路徑>     # plan 最後一次 commit
git status --short -- <plan 路徑>       # 是否有未 commit 的修改
git show HEAD:<plan 路徑> | diff - <plan 路徑>   # 已 commit 版本 vs 工作區
```

判讀與處置：

| 狀況 | 處置 |
|------|------|
| 已 commit、工作區無差異 | 直接進行 |
| 工作區有未 commit 的修改 | **停下確認**——問使用者這些修改是否為定案內容 |
| 本機落後 remote | **停下確認**——`git fetch` 後比對，可能有你沒看到的修訂 |
| plan 檔案根本未 commit | 明確告知使用者，確認這就是要實作的版本 |

**為什麼**：曾發生依據一份未 push 的舊版 plan 實作整個 session，
發現時只能全數 revert。plan 的內容會在討論中反覆修訂，
session 早期讀進 context 的那一份，到動手時未必還是最新的。

長 session 中若中途重讀了 plan，也要重新確認一次——中間可能有人改過。

---

## 2. 宣告範圍，結束時對帳

動筆**前**列出預期會改動的檔案清單（階段 plan 則以階段為單位）。
該階段結束時對帳：

```bash
git diff --name-only          # 未暫存
git diff --cached --name-only # 已暫存
```

比對實際與宣告：

- **實際 ⊂ 宣告**：說明少改的項目是不需要、還是漏了
- **實際 ⊄ 宣告**：逐項說明為何多動了這些檔案

**不是**要求範圍不能變——實作中發現需要多改是正常的。要求的是**變動被看見**，
而不是混在一大包 diff 裡送出。範圍失控最常見的徵兆就是「順手」改了沒宣告的檔案。

---

## 3. 平行路徑檢查

改完任一實作路徑後，**主動搜尋是否存在對應的平行路徑**，並確認是否需要同步修改。

常見的成對關係：

| 一邊 | 另一邊 |
|------|--------|
| JSON 序列化 | MessagePack / XML 序列化 |
| 同步方法 | 對應的 async 多載 |
| 各家 DB provider | 其餘 provider 的同一行為 |
| 快取路徑 | 直接讀取路徑 |
| 實際使用的資料來源 | 已停用但仍在的舊來源 |

搜尋方式：以剛改動的型別名、方法名、常數字串 grep 全 repo，
檢視命中處是否有結構相似但未被修改的實作。

存在平行路徑而**未**同步修改時，必須明確標示並說明理由，不要默默留著。

**為什麼**：曾發生只修了其中一條路徑就宣告完成——App 仍顯示舊值，
因為真正生效的是另一條；也曾漏掉平行的序列化路徑，直到使用者指出。
兩次都是「改的地方確實改對了，但不是全部」。

## 不屬於本 skill

刻意不納入，避免與既有機制重複、稀釋上面三條：

| 事項 | 歸屬 |
|------|------|
| CI 狀態輪詢與失敗分析 | 各 repo 自己的 CI 監測機制 |
| 測試撰寫規範、flaky 判別 | 各 repo 自己的測試規範 |
| commit 前的建置驗證 | 各 repo 自己的 hook（harness 強制，非 skill 能保證） |
| plan 狀態列與階段表格格式 | `plan-write` |

## 常見錯誤

- ❌ 用 session 早期讀進 context 的 plan 版本動工 → ✅ 動筆前以 git 重新確認
- ❌ 發現 plan 未 commit 仍逕自實作 → ✅ 停下確認這是否為定案版本
- ❌ 完成後才第一次列出改了哪些檔 → ✅ 動筆前先宣告，結束時對帳
- ❌ 「順手」改了宣告外的檔案且未提 → ✅ 超出範圍逐項說明
- ❌ 改完一條路徑就宣告完成 → ✅ 先搜尋平行路徑，確認無漏
- ❌ 把 CI 輪詢、測試紀律也塞進來 → ✅ 那些各有歸屬，重複規範會稀釋這三條
